# Applying migrations 020–022 (manual)

**Status: proposed. These migrations have not been executed by the assistant.**
They are additive and do not delete tables, columns, rows, policies, or storage
objects. Review each file before running it.

Run them in **Supabase Dashboard → SQL Editor**, in order, on the project
configured by the app. Never paste or share project keys, service-role keys, or
connection strings.

---

## 0. Before running anything

1. Confirm you are in the correct Supabase project. Check the project reference
   from the dashboard; do not paste secrets.
2. If your project has Point-in-Time Recovery or a recent backup, confirm it is
   available.
3. Confirm the prerequisite schema exists:

```sql
-- Required columns
select table_name, column_name
from information_schema.columns
where table_schema = 'public'
  and (
    (table_name = 'vendors' and column_name in
      ('archived_at','selection_status','agreed_price','quoted_price','payment_status'))
    or (table_name = 'vendor_payments' and column_name in
      ('proof_path','payment_kind'))
    or (table_name = 'inspiration_items' and column_name in
      ('image_path','category','title'))
  )
order by table_name, column_name;

-- Required unique keys for the new composite foreign keys
select conname, conrelid::regclass as table_name
from pg_constraint
where contype = 'u'
  and conrelid in (
    to_regclass('public.vendor_payments'),
    to_regclass('public.inspiration_items')
  );

-- Required helper functions
select proname
from pg_proc
where pronamespace = 'public'::regnamespace
  and proname in ('wedding_has_access','set_updated_at');
```

If `vendor_payments (id, wedding_id)` or
`inspiration_items (id, wedding_id)` is missing, stop: migration 020/021
requires those unique keys. Do not run the migrations partially.

4. Run the approved read-only data impact audit from the implementation plan
   and keep the aggregate output. The audit is still required before approving
   behavior changes; these migrations alone do not change product behavior.

## 1. Apply `020_vendor_payment_proofs_and_idempotency.sql`

1. Open **SQL Editor → New query**.
2. Paste the full contents of
   `supabase/wedding/020_vendor_payment_proofs_and_idempotency.sql`.
3. Click **Run**.
4. Expected result: success with no rows returned.
5. Verify:

```sql
select table_name
from information_schema.tables
where table_schema = 'public'
  and table_name = 'vendor_payment_proofs';

select column_name, data_type, is_nullable
from information_schema.columns
where table_schema = 'public'
  and table_name = 'vendor_payment_proofs'
order by ordinal_position;

select column_name
from information_schema.columns
where table_schema = 'public'
  and table_name = 'vendor_payments'
  and column_name = 'idempotency_key';

select indexname
from pg_indexes
where schemaname = 'public'
  and indexname in (
    'vendor_payment_proofs_payment_idx',
    'vendor_payment_proofs_wedding_idx',
    'vendor_payments_idempotency_idx'
  );

select c.relname, c.relrowsecurity
from pg_class c
join pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'public'
  and c.relname = 'vendor_payment_proofs';

select policyname, cmd, roles
from pg_policies
where schemaname = 'public'
  and tablename = 'vendor_payment_proofs';
```

What this does:
- Adds one table for multiple proof files per payment.
- Adds a nullable `idempotency_key` and a partial unique index for future
  payment creation.
- Does **not** modify existing `vendor_payments` rows or legacy `proof_path`
  values.
- Does **not** move existing proof files.

## 2. Apply `021_inspiration_vendor_options.sql`

1. Open a new SQL Editor query.
2. Paste the full contents of
   `supabase/wedding/021_inspiration_vendor_options.sql`.
3. Click **Run**.
4. Expected result: success with no rows returned.
5. Verify:

```sql
select table_name
from information_schema.tables
where table_schema = 'public'
  and table_name = 'inspiration_vendor_options';

select column_name, data_type, is_nullable
from information_schema.columns
where table_schema = 'public'
  and table_name = 'inspiration_vendor_options'

from pg_indexes
where schemaname = 'public'
  and indexname in (
    'inspiration_vendor_options_item_idx',
    'inspiration_vendor_options_wedding_idx'

select tgname
from pg_trigger
where tgrelid = to_regclass('public.inspiration_vendor_options')

from pg_policies

  and tablename = 'inspiration_vendor_options';
```

What this does:
- Adds reference-only vendor options linked to an inspiration item.
- No FK to `vendors` or `vendor_payments`; no automatic conversion.
- Does not alter existing inspiration items, albums, or files.

## 3. Apply `022_storage_mime_allowlists.sql`

1. Open a new SQL Editor query.
2. Paste the full contents of
   `supabase/wedding/022_storage_mime_allowlists.sql`.
3. Click **Run**.
4. Expected result: success (two bucket rows updated).
5. Verify:

```sql
select id, public, file_size_limit, allowed_mime_types
from storage.buckets
where id in ('payment-proofs', 'inspiration-images');
```

Expected:
- `payment-proofs`: `image/png`, `image/jpeg`, `application/pdf`
- `inspiration-images`: `image/jpeg`, `image/png`

What this does:
- Restricts **new** uploads only.
- Existing WEBP files remain readable; existing objects and policies are not
  modified.
- Application-level validation will also enforce the same allowlists.

## 4. If a migration fails

Stop immediately.

- Copy the exact error code and message.
- Do not rerun a partially reviewed or edited file blindly.
- Do not drop tables/columns/data to work around an error.
- Send the error message back before making further database changes.

The migrations are written to be idempotent where practical, but a failed
statement should still be diagnosed before retrying.

---

## 5. Rollback (only with explicit approval)

These migrations are additive. A rollback would require separate approval and
should not be performed automatically.

If a rollback is explicitly approved:

```sql
-- Restore the previous bucket allowlists
update storage.buckets
set allowed_mime_types = array['image/png','image/jpeg','image/webp','application/pdf']
where id = 'payment-proofs';

update storage.buckets
set allowed_mime_types = array['image/jpeg','image/png','image/webp']
where id = 'inspiration-images';

-- Only if explicitly approved:
drop table if exists public.vendor_payment_proofs;
drop table if exists public.inspiration_vendor_options;
alter table public.vendor_payments drop column if exists idempotency_key;
```

Do **not** run the rollback SQL as part of normal application. It removes new
tables/indexes/columns; keep it for an approved emergency only.
